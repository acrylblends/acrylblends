# 1.1.0

A page follows its state over one WebSocket, so eight windows of a board no longer use up the browser's connections; a panel left open while the app restarts keeps working; and the five things the final macOS walk of the workshop guide found: the agent drives the page that asked, the app honours `PORT` and `HOST`, the appearance reaches every open window at once and the pages the agent builds, and the "Agent is driving" bar stays up for the whole run.

## Added

- **`watch(key, onValue)` of `/api/state/client.js`.** A cell of `ctx.state` is followed in a page with

  ```js
  import { watch } from '/api/state/client.js'
  const stop = watch('board.cards', (cards) => render(cards))
  ```

  The callback gets the value now and after every change, as the JSON value the server holds (a string stays a string); `stop()` ends it. A third argument, `(error) => ...`, is told of a key that does not exist; without it the console gets one warning. One WebSocket (`GET /api/state/ws`) carries every key of the page. A WebSocket is not one of the six connections a browser allows to one host, and an event stream per key is: three keys in eight windows were 24 streams, and the windows past the sixth loaded only partly (found on macOS with 8 board windows).
- The client retries a lost socket after a delay that grows from 250 ms to ten seconds, subscribes every key again and does not repeat a value the page already has. A server that is silent for 45 seconds counts as gone (it writes a ping every 15). A page that is hidden for good lets its connections go, because the back/forward cache would keep them open, and opens them again when it comes back.
- **Where the WebSocket cannot open** (no `ws` package, a server that does not upgrade, a proxy that does not pass it) each key is followed by its event stream instead, with one console warning. `GET /api/state/<key>/events?json=1` sends every value as JSON; without it a string is sent as it is, as before.
- **Who may open it.** The upgrade needs a loopback peer on the app's own port and a loopback `Host`; the `Origin`, when the request has one, must be exactly the app's own origin and `Sec-Fetch-Site` absent or `same-origin`. A program on this machine that sends no `Origin` (a script, a test) is let in, as it is for the JSON and stream routes; a page of another origin gets 403, and so does a request that names another host (a name that only resolves to this machine, DNS rebinding), with or without an `Origin`.
- `ws` is now a dependency of the `acryl-state` plugin (it was only the door's development dependency), so an app that follows state in production has it. It is loaded when the first socket is wanted.
- The agent template's `AGENTS.md` tells the agent to follow state with `watch` and not with an `EventSource`.
- Gates: `verify:door` section G holds all six connections of a page in real Chrome and checks that `watch` still delivers every change of a key; `verify:desktop` opens eight board windows that each follow three keys and checks that they all load and show each new count.

## Fixed

- **A page left open while the app restarts keeps working.** The panel's token belongs to one start of the app, and in development `node --watch` restarts the app at every change of a file, the guide's first edit included: a page that stayed open sent the old token, the socket closed with 4401 and the panel said "the panel was not accepted (reload the page and try again)". The server now says `accepted` once it has taken the token; when the page is refused (4401 on the socket, 403 on the stream) it asks for a new session and tries once more without the person seeing anything, and only a second refusal is shown. The terminal driver takes a fresh session when it opens too. The token stays per start (a token kept across starts would give a leaked one a longer life, and the retry is needed anyway). The door's page channel and the state socket never had a token and reconnect by themselves. Gate: `verify:door` section K restarts the app under an open page in real Chrome and checks that the same document asks the agent, is looked at through the door and follows a state key again, with no reload; with the retry switched off it fails with the message above.

## Fixed (found by the macOS walk of 1.0.10)

- **The agent drives the page whose panel asked.** With a browser tab left open from an earlier step and a desktop window, a question asked in the window's panel sent every door call to the tab: the window stayed where it was, the hidden tab moved, and the agent reported success. The panel now tells the door which page asked, and until the run ends the calls that name no window go to that page (a page that reloads or navigates during its run stays the one; an explicit `--window` still picks its own). The asking page comes before the page the door last sent somewhere and before the page in front. Gates: `verify:door` section H holds a second tab in front and asks from the panel's tab; unit tests in the door's channel and the panel's socket.
- **`PORT` and `HOST` are honoured.** The `agent` and `blank` templates ignored `PORT` (`PORT=3299` still listened on the app's own number 3991). The instance reads `ACRYLBLENDS_PORT`, then `PORT`, and `ACRYLBLENDS_HOST`, then `HOST`, for every template (the three templates that mapped them in `main.ts` no longer need to). `docs/framework/guides/production.md` has the four variables and a real-server example.
- **The appearance reaches every open window, and the pages the agent builds.** The Settings page saved the choice to the browser's storage and only a reload applied it elsewhere. The template now serves `/appearance.js`: one script tag in a page's head applies the saved choice before the page paints, applies a change made in another window at once, and defines `--bg`, `--fg`, `--muted`, `--surface`, `--border` and `--accent` for the system's light and dark and for the person's choice. The home and settings pages use it, and the template's `AGENTS.md` tells the agent to put the tag in the pages it builds and colour them with the properties (the board the agent built used the system's colours and ignored the choice). Gate: `verify:door` section J changes the appearance in one tab of real Chrome and reads the other tab's background colour.
- **The "Agent is driving" bar stays up for the whole run.** It showed only while one door call was in flight (a run is mostly the agent thinking: the walk saw it in none of 33 frames). It is now up from the start of a run asked for from that page's panel to its end, says "working on your request" between calls, and its Stop ends the run as well as the page's control (a new question allows the agent again). Gate: `verify:door` section I, with an agent tool that takes three seconds and calls nothing.

## Changed

- The names `ws` and `client.js` are routes under `/api/state`, so a state cell cannot be called either (`ctx.state.cell('ws', 0)` throws, saying so). No other key changes.

## Upgrading

Run `npx acrylblends upgrade` in an app made before 1.1.0 to take the new `acryl-state` and its `ws` dependency, then `npm install`. The event stream routes are as they were: a page that opens its own `EventSource` still works, and still holds a connection for as long as it is open, so move it to `watch`.
